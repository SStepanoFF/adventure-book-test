# Як це працює (для новачка)

> Усе нижче описує те, що написано в проєкті. Жодного разу не запускались: ні CI, ні Sonar, ні k6, ні OASDiff.
> Усі параметри запуску: `docs/parameters.md`.

## 1. GitHub Actions (CI)

**Що це.** Сервіс GitHub, який за файлом-інструкцією (`.github/workflows/*.yml`) сам запускає ваші команди на тимчасовій
віртуальній машині. Нічого встановлювати не треба: це частина GitHub. Аналог у Jenkins: `Jenkinsfile` + агент, який
Jenkins піднімає за вас.

**Скільки коштує** (за документацією GitHub): для публічних репозиторіїв безкоштовно й без ліміту (стандартні раннери).
Для приватних: безкоштовний план дає 2000 хвилин на місяць і 500 МБ сховища артефактів. Артефакти й логи за замовчуванням
зберігаються до 90 днів (для публічних налаштовується від 1 до 90 днів).

**Як запустити наш CI:**
1. Створіть репозиторій на github.com (або візьміть копію репозиторію додатка).
2. Скопіюйте цей проєкт у папку `tests/` репозиторію, а `ci/ci.yml` покладіть як `.github/workflows/ci.yml`.
3. `git add . && git commit && git push`.
4. На сторінці репозиторію відкрийте вкладку **Actions**. Це не папка, а веб-сторінка: ліворуч назви workflow, праворуч
   історія запусків. Клік на запуск показує jobs; клік на job показує кожен крок з повним логом. Усередині запуску
   внизу блок **Artifacts** (zip із звітами, traces, логами; їх можна завантажити), а нагорі вкладка **Summary** з нашою
   таблицею результатів і покриття API.
5. Запустити вручну без push: Actions -> CI -> кнопка **Run workflow** (є завдяки `workflow_dispatch`).

**Де це виконується:** на віртуальній машині GitHub (Ubuntu), яка існує лише на час запуску. Логи й артефакти потім
зберігаються на серверах GitHub, а не у вашому репозиторії.

**Як перевірити до push:** синтаксис YAML підсвічує редактор (VS Code з розширенням GitHub Actions) або утиліта
`actionlint`. Повністю запустити workflow локально можна утилітою `act` (Docker), але найпростіше запушити в окрему гілку
й подивитись вкладку Actions. Перший запуск майже напевно знайде дрібні помилки: це нормально.

**Яка структура файлу:** `on:` (коли запускати), `jobs:` (незалежні машини; кожна з чистою папкою), `needs:` (порядок),
`steps:` (команди), `uses:` (готові кроки від спільноти, наприклад `actions/checkout`), `matrix:` (повторити job з різними
значеннями), `if:` (умова), `secrets.X` (приховані значення, як credentials у Jenkins). Наші jobs: `backend`, `frontend`
(вихідні перевірки додатка), `contract` (OASDiff), `quality` (Sonar), `e2e` (основне).

## 2. SonarCloud (статичний аналіз)

**Що це.** Сервіс, що читає код без запуску й знаходить баги, вразливості, «запахи коду» і дублювання. Тепер називається
SonarQube Cloud (старе ім'я SonarCloud ще вживається).

**Акаунт і ціна** (за сторінкою тарифів Sonar): потрібен акаунт GitHub (або Bitbucket/GitLab/Azure DevOps), вхід через
нього. Free-план: публічні проєкти без обмеження розміру, приватні до 50 тис. рядків коду. У Free-плані аналізується лише
головна гілка (тому job `quality` у нас запускається лише на push). Наш проєкт значно менший за 50 тис. рядків.

**Що зробити:**
1. На sonarcloud.io: Log in with GitHub -> створити організацію -> **Analyze new project** -> вибрати репозиторій ->
   метод «With GitHub Actions». Сайт покаже **organization key** і **project key**.
2. Підставити їх у `pom.xml` замість `CHANGE_ME` (`sonar.organization`, `sonar.projectKey`).
3. На Sonar: My Account -> Security -> Generate token. У GitHub: Settings -> Secrets and variables -> Actions -> New
   repository secret `SONAR_TOKEN` зі значенням токена.
4. Push у `main`. Job `quality` зробить аналіз; результат на дашборді проєкту (Issues, Quality Gate, Duplications).

**Перевірити локально (без CI):**
`mvn -DskipTests verify org.sonarsource.scanner.maven:sonar-maven-plugin:5.0.0.4389:sonar -Dsonar.token=<токен>`.
Без акаунта: `docker run -p 9000:9000 sonarqube:community`, відкрити http://localhost:9000 (admin/admin), створити токен
і додати `-Dsonar.host.url=http://localhost:9000`.

**Як переконатися, що налаштування працюють:** додайте в тестовий клас навмисну «вонючку» (порожній `catch`, невикористану
змінну, `String password = "123456";`), запустіть аналіз і знайдіть її у вкладці Issues. Потім приберіть.

**Quality Gate** = набір порогів (нових багів немає, дублювання менше ліміту тощо). Якщо не пройдений, при
`-Dsonar.qualitygate.wait=true` job стає червоним. Покриття коду ми виключили (`sonar.coverage.exclusions`): цей проєкт
і є тестами, покриття тут не вимірюється.

## 3. Контрактне тестування

**Контракт** = файл `openapi.yaml`: перелік endpoint-ів (метод + адреса), їхні параметри, форми запитів і відповідей, коди.

### Рівень 1: перевірка реальних запитів і відповідей (у тестах)

- Працює так: `ApiClient.withContract()` додає фільтр бібліотеки swagger-request-validator. Фільтр бачить кожен запит і
  кожну відповідь, що проходить, і звіряє їх із `openapi.yaml`. Розбіжність = виняток = тест червоний.
- **Лише в цих тестах?** Так, свідомо: `ContractApiTest` (по одному на операцію й тип відповіді: 200, 201, 400, 404, 409)
  і `TestSupportApiTest`. Будь-який інший тест теж може увімкнути перевірку: `new BookService(ApiClient.withContract())`.
  Не робимо це всюди, бо негативні тести навмисно шлють «неправильні» запити (зламаний JSON), і контракт їх би відхиляв.
- **Що саме перевіряється:** чи існує така операція (метод + адреса за шаблоном); обов'язкові параметри шляху й запиту та
  їхні типи/формати; тіло запиту за схемою; чи описаний в операції такий код відповіді; тип вмісту; тіло відповіді за схемою
  (типи полів, enum, формат `uuid`, поля, що не можуть бути `null`).
- **Чого НЕ перевіряє:** бізнес-логіку (чи `health` справді 10). Відсутність поля теж не знайде, якщо воно не в списку
  `required` схеми: у `GameState` такого списку немає, тому відсутнє поле контракт не помітить (це зауваження до самої
  специфікації). Бібліотека не знає, що в спеці `lastConsequence` має `nullable` поруч із `$ref`; якщо контрактний тест на
  цьому впаде, це знахідка про специфікацію.
- **Звідки береться специфікація:** параметр `openapi.spec`. Локально це копія в `src/test/resources/openapi/`, у CI
  (`-Denv=ci`) це справжній файл репозиторію `../openapi.yaml`, тому копія не застаріває.

### Рівень 2: OASDiff (чи не зламали сам контракт)

- **Що це.** Відкрита утиліта (Tufin, написана на Go), що порівнює **дві версії** OpenAPI-файлу й каже, що змінилось, а
  головне, що **ламає клієнтів** (breaking changes): видалений endpoint чи параметр, змінений тип поля, нове обов'язкове
  поле, інший код відповіді. Це відповідь на підказку завдання.
- **Які файли порівнюються.** Еталон `contract/baseline/openapi.yaml` (затверджена версія, лежить у git; зараз це точна
  копія файлу додатка) проти поточного `openapi.yaml` додатка (`../openapi.yaml` у CI; локально шлях передайте
  аргументом: `bash scripts/oasdiff.sh /шлях/до/adventure-book/openapi.yaml`).
- **Що встановити:** лише Docker (скрипт запускає образ `tufin/oasdiff`). Альтернатива: поставити саму утиліту
  (`brew install oasdiff` та інші способи на сторінці проєкту) і виконати `oasdiff breaking <еталон> <поточний> --fail-on ERR`.
- **Як працює скрипт:** копіює поточний файл у `target/`, показує всі зміни (`changelog`, для інформації) і запускає
  `breaking --fail-on ERR`: код виходу 1, якщо є breaking changes, і CI червоніє.
- **Коли еталон оновлювати:** якщо API змінили свідомо, скопіюйте новий `openapi.yaml` поверх еталона й закомітьте.
- **Як перевірити:** зробіть копію специфікації, видаліть у ній endpoint або змініть `type: integer` на `type: string`,
  запустіть `bash scripts/oasdiff.sh <ваша копія>`. Має бути список breaking changes і код виходу 1.
  Без змін скрипт завершується з кодом 0.

Рівні доповнюють один одного: рівень 1 каже «сервер не відповідає специфікації», рівень 2 каже «хтось зламав саму специфікацію».

## 4. k6 (навантаження)

**Що це.** Відкритий інструмент навантажувального тестування від Grafana. Сценарій пишеться на JavaScript, а виконує його
рушій на Go, тому він швидкий.

**Як працює.** `export default function` це сценарій одного **віртуального користувача** (VU). k6 запускає 10 таких VU
одночасно на 30 секунд, і кожен повторює сценарій у циклі (`perf/k6/api-latency.js`): список книжок, старт гри, стан гри.
`setup()` виконується один раз до навантаження (бере id реальної книжки).

**Як вимірюється час.** Для кожного HTTP-запиту k6 міряє `http_req_duration` = час від початку відправки запиту до
повного отримання відповіді (відправка + очікування сервера + завантаження відповіді; без часу на встановлення
з'єднання). **p(95) < 500** означає: 95% запитів швидші за 500 мс, найповільніші 5% у розрахунок порогу не входять.

**Пороги (`thresholds`)** це умови успіху. Якщо хоч одна не виконана, k6 завершується з кодом 99, і CI червоніє.
Є пороги для всіх запитів і окремо для кожного endpoint-а (теги `endpoint:...`).

**Встановлення:** `brew install k6`, `choco install k6` або Docker (`grafana/k6`). У CI встановлює готовий крок
`grafana/setup-k6-action`.

**Запуск:** `k6 run -e BASE_URL=http://localhost:8080 perf/k6/api-latency.js` (бекенд має працювати). Результат: таблиця
в консолі; з `--summary-export=target/k6-summary.json` ще й файл.

**Як перевірити, що пороги справді працюють:** тимчасово змініть поріг на `p(95)<1` (1 мс): прогін має впасти з кодом 99.
Або зупиніть бекенд: впаде поріг `http_req_failed`.

**Важливо:** k6 міряє час API, а не сторінки в браузері. Час сторінки міряє Playwright (наступний розділ).

## 5. Час сторінки в Playwright

`PageLoadPerfTest` міряє від `page.navigate(...)` до моменту, коли на сторінці видно дані (перша картка книжки або текст
секції), тобто враховує мережу, виконання JavaScript і відмальовування. Розігрівальний прохід не рахується, далі береться
**медіана** з `perf.runs` (5) замірів, бо один замір це шум. Бюджет `perf.page-ready-budget-ms` (500). Тест `@Isolated`:
не виконується одночасно з іншими. Запуск: `mvn test -Dgroups=perf`. Мають сенс лише заміри на production-збірці
Angular, тому в CI тег `perf` вимкнений.

## 6. Що таке `-Dgroups=arch`

Опція Maven/JUnit «запустити лише тести з тегом `arch`». `ArchitectureTest` має `@Tag("arch")`, тому запускається лише він
(перевірка архітектури: сторінки лише з локаторами, ядро не знає про додаток тощо). Нічого більше й нічого з додатка
для нього не потрібно. Повний список тегів і всіх інших параметрів: `docs/parameters.md`.
